# Выбор технологии для КИП Helper

Дата проверки: 13 сентября 2026 года.

Рекомендация: сохранить **Dart + Flutter**. В проекте уже реализованы экраны Flutter и используется Material 3. Для справочника с автономными данными и инженерными калькуляторами переписывание на другой стек не даёт подтверждённого выигрыша. Это инженерная оценка для данного проекта, а не универсальный рейтинг языков.

## Что действительно проверено

В `experiments/technology_comparison` находятся сопоставимые модели модулей и расчёты линейного сигнала 4–20 мА. На каждом языке предусмотрены 10 проверок: четыре контрольные точки, пять некорректных входов (нулевой/обратный диапазон, выход за диапазон, NaN, бесконечность), уникальность идентификаторов модулей.

| Язык | Выполненная проверка | Результат |
|---|---|---|
| Dart | Запуск `core.dart` через Dart SDK установленного Flutter | 10 проверок прошли, код выхода 0 |
| TypeScript | `node experiments/technology_comparison/core.ts`, Node v24.21.0 | 10 проверок прошли, код выхода 0 |
| Kotlin | `Core.kt` скомпилирован Kotlin/JVM 2.2.20; JRE 21.0.10 из Android Studio, затем запуск JAR | 10 проверок прошли; компиляция и запуск: код выхода 0 |

Node исполняет TypeScript с удалением аннотаций типов: это **не** проверка типов компилятором `tsc`. Полноценные приложения React Native и Compose не собирались; UI, APK, скорость анимаций и потребление памяти альтернатив не измерялись. Расчётное ядро не доказывает работоспособность мобильного интерфейса.

Java и Kotlin обнаружены в нестандартном расположении Android Studio `D:/Program Files/Android/Android Studio`: JBR в `jbr`, компилятор в `plugins/Kotlin/kotlinc`. Дополнительные стеки для эксперимента не загружались. Воспроизведение компиляции и запуска в PowerShell:

```powershell
& 'D:\Program Files\Android\Android Studio\jbr\bin\java.exe' '-Dkotlin.home=D:\Program Files\Android\Android Studio\plugins\Kotlin\kotlinc' -cp 'D:\Program Files\Android\Android Studio\plugins\Kotlin\kotlinc\lib\*' org.jetbrains.kotlin.cli.jvm.K2JVMCompiler -version experiments/technology_comparison/Core.kt -include-runtime -d build/technology-comparison.jar
& 'D:\Program Files\Android\Android Studio\jbr\bin\java.exe' -jar build/technology-comparison.jar
```

Три сравнительных прототипа специально ограничены линейным преобразованием: они не рассчитывают характеристику термосопротивления и не описывают аварийные сигналы преобразователей. Они не подключены к производственному приложению. Отдельный `review_probe.dart` воспроизводит погрешность обратной НСХ на 100 °C и строгую проверку `SignalRange.contains`; он служит диагностическим примером, не сравнительным тестом языков. В производственном расчёте `rtdMilliamps` эта погрешность учитывается допуском; регрессия покрыта в `test/domain_test.dart`.

## Сравнение для задачи

| Критерий | Flutter / Dart | Kotlin / Compose | TypeScript / React Native |
|---|---|---|---|
| Простота реализации | Уже используется; один язык для модели, расчётов и экранов | Хорошо подходит Android, но потребуется перенос существующих экранов | Краткие модели и формулы; потребуется новый проект и перенос экранов |
| Читабельность | Явные типы, обычные классы, декларативные виджеты | Компактные data class и декларативные функции | Компактные типы объектов; нужны отдельные проверки типов |
| Новые модули | Общая модель справочника и экран отображения данных | Та же модель архитектуры реализуема | Та же модель архитектуры реализуема |
| Визуальная часть | Готовые Material-компоненты, управление темой и компоновкой | Нативный Android toolkit, тесная интеграция с платформой | React-компоненты; фактический дизайн требует самостоятельной реализации и проверки |
| Цена перехода сейчас | Минимальна | Переписывание приложения | Переписывание приложения |

Все три стека подходят для такого класса приложений. Лаконичность формулы практически одинакова; масштабируемость больше зависит от отделения данных справочника, расчётного ядра и UI, чем от языка. Добавление оборудования должно сводиться к новому модулю данных, а новый тип калькулятора — к отдельной функции и экрану. Большой `main.dart` следует разделять по ответственности, без ненужного усложнения архитектуры.
