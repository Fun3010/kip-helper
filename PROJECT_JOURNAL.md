# Журнал разработки и передачи проекта КИП / помощник

Обновлено: 5 октября 2026 года. Часовой пояс: Asia/Yekaterinburg (UTC+5).

Этот файл — основной контекст продолжения задачи. Он фиксирует требования,
действия, проверяемые выводы, решения и их краткие основания. Это не запись

дальнейшие действия добавляются по мере выполнения.

## 1. Подробное техническое задание для следующего разработчика / ИИ

Продолжить разработку существующего проекта Flutter в
`D:\VSCode\KIPHelper\kip_helper` до получения работающего Android-приложения,
которое устанавливается из APK. Пользователь хочет интерактивный справочник
«всегда под рукой» для слесаря КИПиА с инженерными калькуляторами и удобным
интерфейсом телефона. Недостаточно исправить синтаксис: необходимо проверить
расчёты, достоверность справочника, мобильную компоновку, сборку и запуск.

Перечень приборов, названный пользователем:

- Siemens SIPART PS2: настройка позиционера, инициализация, диагностика.
- СУ-1С: назначение контактов, подключение, состояния уровня и исправности.
- СОКРАТ и РэмТЭК: конечные положения, настройка, диагностика / коды.
- Biffi: электроприводы; имеющиеся сведения относятся к ICON 2000.
- СТМ-10 и СТМ-30: сигнализаторы горючих газов.
- Термосопротивления: соответствие температуры, сопротивления и выходного
  тока 4–20 мА преобразователя; также единицы температуры и давления.

Пользователь просил выбрать оптимальный язык, попробовать несколько вариантов
по простоте кода, читабельности, масштабируемости, добавлению модулей и
визуальному качеству. Он разрешил работу отдельных агентов, исправления и
необходимые итерации проверки; несколько раз подтвердил «продолжай».

Требование результата: APK для установки на Android, исходники, проверяемые
результаты тестов. Не обещать устранение всех возможных ошибок: фиксировать
фактически выполненные проверки и оставшиеся ограничения. Не считать
widget-тесты подтверждением установки APK на телефон.

14 сентября добавлено требование регулярно вести этот журнал, чтобы другая
модель могла продолжить работу без восстановления всей переписки.

### 1.1. Назначение, аудитория и границы продукта

Разработать автономное русскоязычное Android-приложение «КИП / помощник» для
слесаря КИПиА, наладчика и специалиста эксплуатации. Основной контекст работы —
объект, где нужно быстро найти проверенное описание настройки или пересчитать
измеряемую величину. Пользователь взаимодействует с экраном телефона;
приложение не подключается к промышленной сети и не управляет оборудованием.

Это справочник и расчётный инструмент. Он не выполняет поверку, не выдаёт
допуск к работам, не обнаруживает исправность реального оборудования и не
заменяет паспорт установленного прибора. Не добавлять интерфейсы Modbus/HART,
Bluetooth-управление, облачный сервер, регистрацию, рекламу и подписки без
нового задания. Отсутствие этих функций не считать дефектом текущего объёма.

Все заявленные в поставке функции должны работать из установленного APK.
Сведения, не подтверждённые для конкретного исполнения, не выдавать за готовую
универсальную инструкцию. Частичное покрытие вариантов модели явно обозначать.

### 1.2. Платформы, поставка и язык реализации

- Основная платформа: Android на физических телефонах; эмулятор используется
  для дополнительной воспроизводимой проверки.
- Текущая сборка: minSdk 24 (Android 7.0), targetSdk/compileSdk 36.
  Это технические параметры выбранной версии Flutter, а не требование
  пользователя поддержать каждый когда-либо выпущенный Android.
- APK включает ABI arm64-v8a, armeabi-v7a и x86_64; конкретный APK должен
  проверяться по манифесту и подписи, а не только по имени файла.
- Поставка: исходники, lockfile зависимостей, инструкции, журнал, отчёт
  проверки и release APK. Прямая установка должна обходиться без Flutter SDK
  на телефоне. Публикация в магазине не входит в задание.
- Выбор языка подтверждается сравнительными прототипами и описанием
  ограничений эксперимента. Фактический выбранный стек — Flutter/Dart.
- Debug-подпись release допустима для текущего локального испытания и должна
  быть явно указана. Постоянное распространение требует отдельного управляемого
  ключа; его потеря несовместима с обновлением уже установленной версии.

| REF-02 | Поиск по названию, исполнению, коду и текстам | Известный запрос находит нужное; неизвестный показывает пустой результат |
| REF-03 | Поиск без учёта регистра и с удалением пробелов по краям | Проверка смешанного регистра и пробелов |

| REF-05 | Универсальный экран разделов с раскрытием и поиском | Раздел раскрывается, содержимое прокручивается; доступно раскрытие всех |

Минимальное содержимое:

1. SIPART PS2: условия подготовки; связь типа привода с настройкой;
   автоматическая инициализация 4.INITA; смысл RUN1–3; действия для
   идентификации незавершённой настройки и ссылки на разделы РЭ.
2. СОКРАТ: подготовка; запись закрытого и открытого положений для указанного
   блока/ПО; подтверждённые коды аварий и единицы защит. Не выдавать
   увеличение момента за универсальный способ устранения неисправности.
3. РэмТЭК: конкретное исполнение 9000.V и РЭ; предупреждение об отсутствии
   прежнего останова после сброса; порядок записи 0/100%; область применения
   метода по двум точкам; ограничения при невозможности полного хода.
4. СУ-1С: карта контактов по конкретному РЭ; логика уровня и исправности;
   интерактивное переключение состояния среды на логической схеме.
   Переключатель иллюстрации не представляет команду реальному прибору.
5. Biffi: точное исполнение ICON 2000, различие аварии/предупреждения,
   просмотр сообщений и ссылка на руководство. Другие серии не подразумеваются.
6. СТМ-10: назначение, идентификация канала/датчика/газа, подготовка к проверке.
7. СТМ-30: индикация, применимая метановая шкала, подтверждённые сообщения
   конкретных модификаций. Не смешивать %НКПР с объёмной долей газа.

### 1.4. Функциональные требования к калькуляторам

| ID | Требование | Проверка результата |
|---|---|---|
| CALC-01 | Температура C/F/K, прямое и обратное направление | Опорные точки и все пары единиц |
| CALC-02 | Восемь единиц давления | Опорные коэффициенты и все пары единиц |
| CALC-03 | Температура в сопротивление и обратно для семи НСХ | Табличные значения и границы каждой характеристики |
| CALC-04 | Ток 4–20мА из величины и величина из тока | 4/12/20мА, прямое/обратное вычисление |
| CALC-05 | Связь RTD с линейным преобразователем | Температура и заданный диапазон определяют ток |
| CALC-06 | Нижняя/верхняя границы задаются пользователем | Нулевой и обратный диапазоны отклоняются |
| CALC-07 | Числа со знаком, запятой/точкой и экспонентой | Набор unit-тестов parseNumber |
| CALC-08 | Явная ошибка вместо ложного нуля | Пустая строка, мусор, NaN, Infinity, overflow |
| CALC-09 | Обновление результата после ввода и выбора единиц | Widget-тест и ручная проверка |
| CALC-10 | Читаемый результат с единицей и возможностью копирования | SelectableText, проверка длинного числа |

Численные правила приведены в разделе 4 и являются частью ТЗ. Независимые
табличные точки обязательны: совпадение прямой и обратной функций само по
себе не доказывает правильность НСХ. Разрешённая численная погрешность
обратной НСХ в тестах — порядка 1e-8°C; округление отображения отделено от
внутренней точности. В интерфейсе обычные числа отображаются до четырёх знаков
после запятой, очень большие/малые — в экспоненциальной форме.

### 1.5. Пользовательские сценарии

**Сценарий A: настройка привода.** Открыть каталог → найти прибор → сверить
исполнение → раскрыть подготовку и конечные положения → при необходимости
открыть полное РЭ. Возврат должен возвращать в каталог без аварии.

**Сценарий B: поиск аварии.** Ввести код, например A01 → открыть СОКРАТ →
найти раздел аварий → прочитать применимость. Неизвестный код не должен
приводить к показу всего списка как будто найдено совпадение.

**Сценарий C: проверка RTD.** Открыть расчёты → выбрать НСХ по паспорту →
выбрать ввод температуры либо Ом → получить вторую величину → задать
температуры 4/20мА → получить ток. За пределами НСХ или диапазона отображается
объяснение, а не правдоподобное неверное значение.

**Сценарий D: токовая петля.** Указать нижний/верхний предел в одинаковых
единицах → ввести величину или ток → получить пересчёт. Для внешнего
диапазона помечается экстраполяция, аварийный ток не выдаётся за достоверное
измерение. Квадратнокорневая характеристика расхода не поддерживается.

**Сценарий E: контакты СУ-1С.** Сверить номер РЭ → раскрыть схему → изменить
состояние среды → видеть замыкание 1–3 или 1–2; 4–5 в исправном состоянии
замкнуты. Физическое расположение контактов по рисунку не определять.

### 1.6. Требования к интерфейсу и устойчивости

- Русский интерфейс и локализованные стандартные элементы Material.
- Три главных раздела: справочник, расчёты, сведения о приложении.
- Material 3, единая цветовая система, светлая/тёмная темы, собственная иконка.
- Основной контент рассчитан на телефон; длинные инструкции и формы
  прокручиваются. На большом экране ширина ограничена для читабельности.
- Проверяемая базовая ширина — 320 logical px; увеличенный шрифт 1,5×.
  Физический телефон дополнительно проверяется с собственной клавиатурой,
  масштабом, системными панелями и поворотом.
- Элементы ввода и выбора не должны вызывать RenderFlex overflow,
  перекрываться результатом либо делать нижние поля недоступными.
- Некорректный ввод не вызывает необработанных исключений.
- Контроллеры освобождаются при уничтожении экрана; callback после await
  проверяет существование context перед показом сообщения.
- Открытие источника выполняется через штатный внешний обработчик;
  отсутствие браузера/отказ обработчика отображается понятным сообщением.
- Отсутствуют сбор телеметрии измерений, аккаунты и обязательная сеть.
  Полные руководства в текущий APK не включены — это отображается в UI.

### 1.7. Архитектурные и эксплуатационные требования

Расчётное ядро не импортирует Flutter. Типизированные модели отделены от
конкретных данных, универсальный экран — от содержимого. Новые формулы
добавляются с валидацией и независимыми тестами. Не возвращать вычисления
в обработчики кнопок и не создавать новый монолит main.dart.

Не хранить абсолютные пути SDK в отслеживаемых проектных настройках.
Секреты подписи не коммитить. pubspec.lock сохранять для воспроизводимости.
Не изменять глобальную политику PowerShell ради запуска скриптов; если
скрипты запрещены, разрешённые команды можно выполнить из терминала отдельно.

На Windows при Pub cache на C: и проекте на D: проверять Kotlin incremental
cache. В текущем окружении он отключён настройкой kotlin.incremental=false
из-за подтверждённой ошибки относительных путей между дисками. Это влияет
на скорость Kotlin-пересборки, но не на расчёты или данные приложения.

### 1.8. План верификации и критерии приёмки

1. Форматирование Dart и `flutter analyze` без ошибок/предупреждений проекта.
2. Unit-тесты всех калькуляторов, граничных и некорректных входов.
3. Проверки целостности/поиска каталога и источников.
4. Widget-тесты навигации, выбора НСХ, раскрытых инструкций, двух тем,
   малого экрана и увеличенного текста.
5. Просмотр реальных снимков, не только отсутствие исключений тестера.
6. Успешная release-сборка, проверка манифеста, ABI, версии и подписи APK.
7. Установка APK на эмулятор; запуск, основные сценарии, логи приложения.
8. Установка той же сборки на доступный физический телефон с разрешения
   пользователя; запуск, ввод, навигация, поворот, возврат из фона.
9. Зафиксировать модель и Android, версию APK, размер/хеш и фактические
   результаты. Не заявлять тесты на устройствах, которых не было.
10. Передача APK, исходников, README, отчёта и актуального журнала.

Блокирующие дефекты: APK не устанавливается/не запускается; приложение
падает; формула даёт неправильную НСХ или единицы; неверная распиновка выдана
как подтверждённая; не работает основная навигация; нижние поля недоступны.
Замечания инструментального окружения следует различать с ошибками приложения
и описывать, если они не влияют на созданный артефакт.

Число итераций определяется найденными дефектами. Не прекращать работу
только после первого успешного теста; одновременно не выполнять бесконечные
повторные прогоны неизменённого кода без новой причины.

## 2. Существенные ограничения и решения

1. Оставлен **Flutter / Dart**. В проекте уже был Flutter, его Material 3
   подходит для интерфейса; переписывание на альтернативный стек не показало
   необходимого выигрыша. Расчётные прототипы Dart, TypeScript и Kotlin
   фактически прошли по 10 одинаковых проверок. React Native / Compose UI
   не собирались; сравнение не является измерением их мобильных интерфейсов.
2. Офлайн работают карточки, поиск и все расчёты. Полные PDF не включены в APK:
   источники открываются во внешнем браузере и требуют сети.
3. Название прибора не задаёт однозначно исполнение. Пользователю задавался
   вопрос о шильдиках/изготовителях; он повторил перечень и добавил Biffi,
   СТМ-10/30, но не указал точные модификации. Карточки явно ограничены РЭ,
   версией ПО или серией. Не распространять распиновки и процедуры на все модели.
4. Используются первичные тексты руководств / стандарта. РЭ СУ-1С найдено
   на зеркале поставщика, что отмечено в интерфейсе и аудите.
5. Новый прибор добавляется данными, без нового экрана. Расчёты отделены от UI.
6. Android release пока использует debug signing из исходного шаблона. Такой
   подписанный APK устанавливается для локальной проверки; для постоянного
   распространения требуется сохраняемый ключ. Не публиковать приложение
   и не создавать внешние учётные записи без отдельного запроса.
7. До начала работ пользователь уже изменил `lib/main.dart`: удалил два
   избыточных `.toList()` в галереях. Затем по расширенному заданию монолит
   заменён модульным приложением, галереи отсутствующих изображений убраны.
   Коммиты и откаты пользовательских изменений не выполнялись.

## 4. Расчёты: правила, которые нельзя потерять

- Ввод принимает запятую/точку, пробелы по краям, знак и экспоненту.
  Пустое/нечисловое значение, NaN и бесконечность отклоняются, не заменяются нулём.
- Температура: C/F/K, значения ниже абсолютного нуля отклоняются.
- Давление: коэффициенты к паскалю; отрицательное избыточное давление допустимо.
  Преобразование единиц не переводит избыточное давление в абсолютное.
- `SignalRange`: конечные пределы и `upper > lower`.
  `I = 4 + 16 × (X − lower)/(upper − lower)`. Обратная функция также реализована.
  Экстраполяция на отдельном экране сигнала явно обозначена. Это линейный
  преобразователь, не квадратнокорневая характеристика расхода.
- Pt100/Pt500/Pt1000: α=0,00385; A=3.9083e-3, B=-5.775e-7, C=-4.183e-12.
- 100П/50П: α=0,00391; A=3.9690e-3, B=-5.841e-7, C=-4.330e-12.
- Для платины `R/R0=1+A*t+B*t²`, а ниже 0°C дополнительно `C*(t−100)*t³`.
  Диапазон номинальной характеристики −200…850°C.
- 100М/50М: α=0,00428; 0…200°C линейная характеристика;
  −180…0°C добавлены члены ГОСТ `-6.2032e-7*t*(t+6.7)+8.5154e-10*t³`.
- Обратная НСХ вычисляется бисекцией по монотонной характеристике.
  `rtdMilliamps` учитывает погрешность обратного расчёта до 1e-8°C на границе,
  иначе 99.99999999999991°C ошибочно отклоняется при нижнем пределе 100°C.
- Рабочий диапазон конкретного термометра может быть уже диапазона НСХ.
  Погрешность прибора и сопротивление проводов не моделируются.
- Ток зависит от температуры и настройки преобразователя, не линейно от Ом.
